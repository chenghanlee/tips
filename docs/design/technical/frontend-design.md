# Frontend design

Date: 2026-09-20. Status: incorporates the holistic architecture, backend and frontend consensus alongside prior UX and owner decisions. This document states the selected browser behavior; implementation and full browser verification remain outstanding.

## Scope

This document owns LiveView and frontend design: pages, navigation, components, forms, browser interactions, presentation state, accessibility, and frontend testing.

Accept necessary complexity when it makes the user's experience simpler. Judge a control or state by the effort it removes across the whole task, including keyboard, touch, accessibility and failure recovery. Preserve writing, show progress automatically, offer useful actions at the point of need, and avoid making users translate implementation limits into manual work. Fewer controls or hooks alone is not a reason to require repeated clicks, external file conversion, manual copying or starting over. Keep the smallest interaction that makes the task clear and easy.

Follow the [software architecture](software-architecture.md). The [backend design](backend-design.md) owns business operations, authorization, persistence and background work. The [data model](data-model.md) owns the canonical schema and content invariants. The [frontend review](../../brainstorm/idioms-v2-frontend-review.md) records the earlier why-chains and consensus; the [UX frontend review](../../brainstorm/ux-idioms-frontend-review.md) records the conventions-and-simplification debate, the user-effort reassessment and the unexecuted acceptance scenarios. This document states the selected design.

The [holistic architecture](../../brainstorm/holistic-architecture-review.md), [backend](../../brainstorm/holistic-backend-review.md) and [frontend](../../brainstorm/holistic-frontend-review.md) reviews record the cross-layer decisions applied here. This document owns browser draft state and navigation; the backend owns receipts, authorization and operation outcomes, and the data model owns schema and concurrency invariants. Keep one owner for each procedure and link to it.

## Foundation

Use Phoenix LiveView as the default for interactive pages, with shared HEEx components and conventional controller routes where needed. Keep the frontend in the same application and release as the backend.

Use the owner's selected shadcn design language through [SaladUI](https://github.com/bluzky/salad_ui), with native Phoenix/HEEx components and the existing LiveView architecture. Fable, or an Opus model, owns visual design; Fable is the designated implementation-plan design owner. Retain Phoenix's explicit layout composition and adapt shared components to Tips. Pin and verify the SaladUI/Phoenix/LiveView/Tailwind combination before broad UI implementation, including hooks, form errors, keyboard focus, live patches and reconnect. Use the library where it fits and adapt individual components only when needed. The component choice does not replace the native select/details behavior or transfer editor, upload, search or draft state out of the page. Exact visual compositions and component styling are delivered in the [implementation plan's visual-design package](../../implementation/implementation-plan.md#work-packages-and-dependencies).

Render readable public content in the initial HTML response, then connect for interactive updates. For search, `handle_params` calls the same bounded Content operation synchronously on the disconnected and first connected load; later parameter changes, including page changes, use named async work. Accept duplicate initial retrieval and normal ranking changes, without a separate keyword-only first render or an empty connected render that replaces readable results. Connected interactions require the JavaScript client. Keep browser-local behavior in Phoenix JS commands or small hooks.

Use LiveView's interaction and lifecycle APIs and let Phoenix handle the transport. A separate WebSocket or server-sent-event protocol needs a concrete integration requirement. This applies Chris's transport discussion at 06:53–08:26 in the [supplied interview](software-architecture.md#interview-transcript); it does not imply that server-sent events are unsuitable for every application.

## Boundary with the backend

LiveViews and controllers call context functions. Pass caller information through the application's scope. The frontend presents results and errors; context operations enforce permissions and coordinate durable changes.

Anonymous visitors can read public content. Require sign-in before opening a new-tip or review editor, then return to the intended form. Put editor routes through the authenticated plug and live-session/hook boundary; entry must not bypass the plug through same-session live navigation. TipsWeb carries one validated `return_to` through login/registration, the email link, confirmation form and controller redirect. Allowlist local routes when accepting and consuming it; checking only for a leading slash is insufficient. Use the generated GET-session destination as fallback, not as the only carrier: public LiveView vote/report events cannot write Plug session state and another-browser confirmation lacks the original cookie. Keep the destination through form rerenders and validation errors. Carry neither drafts nor pending mutations. Use live navigation only when actual router/live-session boundaries permit it; otherwise use ordinary navigation with the same destination. Recheck access after authentication. Adapt ownership filters to shared content; authors/moderators receive only capabilities returned by Content.

First-time signup is one registration form: an autogenerated public handle the user can keep or edit, and the email address, submitted together. State on that form that the handle cannot be changed afterward, including if they keep the suggestion. After magic-link verification, return to the intended editor. Existing users sign in with email. Follow the [backend signup contract](backend-design.md#first-time-signup).

LiveView state represents the current page and interaction; committed content lives in Postgres. A remount reloads committed state and an old scope does not grant permanent permission. Use the backend's single admission helper for every mutation and privileged read, including video status checks and author/moderator projections. Retain only the server-derived session-row reference bound to the mounted user, not the bearer token, and use the shared Accounts expiry/context/revocation definition. Keep the reference out of templates, client events and browser storage. Truly public reads and rendering need no repeated token query.

Session-family disconnects provide prompt feedback but are not authorization enforcement. The backend’s shared admission helper checks current token validity. A failed admission means privileged work must stop; preserve on-screen input and local drafts, explain sign-in, and carry the editor destination through authentication. Do not silently reload first or force a redirect after failed autosave. An explicit sign-in exit follows the existing leave warning for unsaved values or image bytes. Restore only for the same account; authentication cannot silently transfer ownership. Work already admitted may finish under the backend’s business-eligibility rules.

When signup receives an already registered email, explain that the address is registered and offer Sign in, preserving the intended local destination. This follows Phoenix's generated feedback and intentionally reveals account existence; do not claim enumeration resistance.

An unfinished signup expires seven days after registration. Keep the verification screen focused on the next action: check the inbox, or request another link. Explain the seven-day deadline only when it causes a rejection, with a clear Restart signup action; resending a magic link does not extend the deadline. A merely expired magic link for a still-valid registration can be requested again. The previous handle may no longer be available after registration expiry.

## Pages to design

| Area | Frontend topics |
|---|---|
| Browse and search | Tip summaries, filters, sorting, pagination, and empty results |
| Tip page | Tip content, reviews, voting, images and video, and author/moderator controls |
| Publish and edit | Forms, validation, attachment previews, media selection, and save outcomes |
| Accounts and profiles | Magic-link flows, account settings, and public contributions |
| Inbox | Notification presentation and the existing read-state behavior |
| Moderation | Paged flag queue and permitted moderation actions |

Use dedicated routable pages for creating and editing tips and reviews, with one editor LiveView module per content kind and `:new`/`:edit` actions in the same authenticated live session. The page owns the form lifecycle; function components/helpers share behavior. Do not embed review editors in the tip page or use modal editors. The explicit publication-to-edit handoff patches within that LiveView to preserve page-owned uploads; `handle_params` freshly authorizes the target through Content. Keep upload configuration and relevant DOM identity stable during that transition. Unrelated target/account changes must never inherit its values. After content acknowledgement and safe draft clearing, navigate to the tip or the review’s single-review URL. Hidden content follows authorized presentation. Failed, divergent or uncertain outcomes preserve the editor until resolved.

This is the agreed application of [Phoenix's page-navigation pattern](https://phoenix-live-view.hexdocs.pm/live-navigation.html). Exact route paths and the remaining LiveView boundaries are still to be designed.

## Navigation and content

Public profiles show one newest-first contributions list with each row labelled Tip or Review, ordered by `(created_at DESC, kind ASC, id DESC)` so equal timestamps and independent ids stay deterministic. A labelled native Contributions select offers All / Tips / Reviews and lives in the URL; All is the default. Reuse the shared immediate-change and focus behavior below. Returning this single selector to All clears the profile filter; no separate reset action is needed. Changing it resets to page one. The list uses the shared page navigation below and the existing visibility rules, including masked deleted-parent labels on reviews. There are no tabs and no inactive-list state.

Discovery uses a compact toolbar: the owner-selected labelled native Hot/New sort select for browse ordering, and three labelled native `<select>` controls for Technique, Model and Environment, each with an All option. Changing a select updates the URL and the results immediately; there is no Filters panel, Apply action, pending state or applied-chip row. Reuse the same labelled-select components and behavior for review sort/filters and the profile contribution filter. Label the behavior before the controls ("Changing a selection updates the list"), keep focus on the changed control, never navigate merely on focus, and keep native keyboard selection working. If the chosen LiveView patch breaks native selection or causes a context change, fix the patch rather than reintroducing a panel. The sort dropdown applies to feed/browse ordering; it does not add Hot/New ordering to relevance-ranked search results.

For browse, search and normal-review filter groups, show one "Clear filters" action beside the selects whenever any filter is active, including when results are empty. It sets that group to All, preserves the last submitted query and applicable sort, and returns to page one. It never submits text still being edited in the search field. Each select can also be reset individually to All.

Model and Environment filters match the tip author's reported setup; label them so a reader does not read them as the reviewer's setup. Exact matching and combined AND semantics are retained; free-text search is not a substitute for them.

Keep URLs meaningful for sharing, refresh, and browser navigation. Browse URLs carry filters, sort and page; search URLs carry the submitted query, filters and page, with fixed relevance ordering and no selectable sort. Normal tip-page review URLs carry reviewer filters, review sort and review page; the contribution filter and page are parameters on a profile.

Submitting an empty or whitespace-only search query performs no retrieval, generates no embedding, changes no URL and resets no pagination. Show one message from the shared trim check, "Enter a task or keywords to search," and focus the field. Do not also set `required`, which whitespace passes and which would produce a competing native message. Keep the existing results, their heading and the applied filters. Clearing or typing in the input alone also leaves the last submitted search unchanged.

Submitting a search from filtered browse carries the applied Technique, Model and Environment values into the search URL, where the same selects show them; readers set a select to All or use Clear filters to broaden results while retaining the query. The browse Hot/New sort does not carry into relevance-ranked search. This adapts [Reddit's scoped-search convention](https://support.reddithelp.com/hc/en-us/articles/19696541895316-Available-search-features) to Tips' filter dimensions.

Separate browse and search into page LiveViews that share the filter controls, page navigation and tip-row components. Browse uses `/?sort=hot` or `/?sort=new`; search uses `/search?q=scoped+edits`. Technique, model, environment and page are URL parameters on either page. Browse owns its page lifecycle over current rankings; search owns its submitted-query, async loading, and rerun-per-page lifecycle. Search retains relevance ordering rather than inheriting the browse sort. Use live navigation between pages and URL patches for parameter changes within a page, subject to Phoenix's live-session boundaries.

### Paged reading lists

Every list uses URL page navigation with Previous and Next links and a current-page indication: browse, search, profiles, the inbox and the moderation queue at twenty rows, a tip's normal review list at thirty. Each LiveView holds only its current page in ordinary assigns; there are no streams, accumulated rows, seen-id sets, append or reset modes, loaded-depth reconstruction or inactive-list caches. Keep stable, ordinary DOM ids for labelled controls, rows and hooks; a per-row vote update refreshes that visible row from the confirmed response without a second page cache.

Normal lists derive "has more" from one-row lookahead; search derives it from its existing bounded ranking window. Never present a total result count. No arbitrary page cap exists outside the bounded search window; measure deep-offset performance on the target corpus rather than assuming it. Rankings can change between page requests, so a tip may repeat or be missed across pages as votes and content move; do not promise a frozen order, no-repeat traversal or exact scroll restoration. Changing query, filters, sort or profile filter resets to page one. An empty or out-of-range page offers Previous and First page. Invalid page syntax normalizes or rejects consistently.

### Search retrieval and list state

Rerun bounded search for every requested page. Query, applied filters and page live in the URL. There is no search snapshot, lifetime or guarantee of reproducing an earlier order.

`handle_params` performs the bounded synchronous disconnected and first connected loads described above. After that, changed URL parameters and explicit Retry call one `begin_results` helper with the current normalized query/filter/page state. The helper cancels the prior named task with `cancel_async`, starts `start_async(:results, ...)`, and owns loading for the latest request. Submit/filter handlers only normalize intent and patch the URL; ordinary unchanged submissions remain no-ops. Retry deliberately reruns the same requested page without a fake URL nonce or history entry. Use a first-connected-load assign to distinguish initial synchronous work from later requests. Same-name supersession ignores old results but does not itself stop work. Ignore cancellation exits such as `{:shutdown, :cancel}` instead of showing an error; retain framework stale-result suppression rather than an application generation protocol. Pass only needed values, never the socket. Cancellation cannot retract provider work already received; backend concurrency, queue and total-deadline limits still apply. Pin and test these framework behaviors.

A persistent results heading names the submitted query and applied filters; typing changes nothing. A changed submitted query or filter set shows loading under the new heading; old rows are never shown under new filter values. A page navigation failure keeps the requested location and offers retry for that page; it never shows an old page under a new number. Blank submissions show the blank-search message without retrieval or navigation; submitting an unchanged query/filter set does not fetch again.

On Back, the browser returns to the previous page URL and the page renders from it. On reconnect, the current page URL renders again. There is no Back-only "Results refreshed" notice and no Back detector; truthful connection and retry feedback remain for states the application can identify. Verify during implementation that Back restores a useful reading position on the prior page as well as its URL, without promising a frozen ranking. Do not add a history/storage subsystem for navigation.

The main page contains a Hacker News/Reddit-style tip feed with Hot/New sorting, a search box that carries the task framing in its label and helper text, and the three native filter selects. Curated technique and model labels on tip rows are separate links. Within browse or search, a link sets only its corresponding filter, preserving other filters, the submitted search query or browse sort, and resetting page one. On tip or profile pages, links on tip metadata open browse with that single filter and default Hot ordering; they do not infer discovery state from browser history. Free-text model names render as plain text everywhere because they have no exact model-id filter. Reviewer setup is displayed as metadata, not as a link that changes parent-tip filter eligibility. Use the same feed component for filtered browse listings and the same summary component for search results, with matching-review excerpts where applicable. Keep the applicable query, filter, sort and page state in the URL under the per-page rules above. Follow the [backend feed contract](backend-design.md#main-feed-and-clickable-filters).

Model filters match the tip author's selected model. Show reviewers' models with their individual reviews inside the tip page; those models do not change the tip's filter eligibility. Keep the tip's setup metadata distinct from a matched review excerpt so readers do not mistake a reviewer's setup for the tip author's.

Keyword fallback is invisible to readers: render the returned results normally without a degraded-search notice. If search fails entirely, show retry feedback rather than "no matches." Recovery of meaning-based search can affect the next requested page because retrieval reruns each time.

Submit a text query with Enter or the Search button. Do not run full search while typing and do not provide autocomplete in the MVP. Keep existing results associated with the last submitted query until a new search is submitted; typing alone does not update the URL or reset pagination.

For a filtered search with no matches, keep the entered query and current filter values visible. Offer setting any filter to All, Clear filters and query editing; do not broaden the search automatically or show out-of-filter suggestions. A search error displays retry feedback, not the no-matches message.

Hot/New is a shared feed over current rankings with page navigation. Each page renders the current ranking at request time, so a tip can appear on two pages or be missed as votes move it; this is the accepted trade of page navigation. Browser refresh reloads the URL page; sort/filter changes start at page one. Search reruns its bounded relevance ranking for each requested page.

Render compact text-only feed rows like Hacker News, with title, tags/model, author, age, net score, review count, and compact Helpful / Not helpful buttons. Reuse the detail vote control's labels, selected state, pending feedback and toggle behavior; the summary shows net score rather than two counts. The title is the row's link; tag and author links are separate, comfortably spaced targets, never nested inside another link. Open the tip to view images, GIFs, and videos. Use the same text-only summary in filtered listings and search; retain matching-review excerpts in search results, bounded to about two hundred characters, escaped, labelled with their source (Review, Prompt, Result, or Reviewer setup) and rendered as their own link. Feed rows have no media thumbnail, embedded player, or autoplay.

Each non-empty Prompt and Result block on a published tip or review has a labelled Copy action ("Copy prompt", "Copy result") implemented by one small hook over the Clipboard API. Copy the raw stored text with its whitespace, never rendered `innerText`, labels or line numbers. Say "Copied" only after success, with a polite status message; on denial or a missing API say to select and copy manually. Ordinary text selection still works. No clipboard reads, backend operation, copy tracking or whole-tip export.

On tip and review pages, image/GIF previews link to the full-size asset in a new tab through a separately named action. Videos render inline through the provider's player: a poster from `/media/:id/thumbnail` and a click-to-play control that, on Play, loads an iframe whose source is `/media/:id/watch`; that route authorizes and signs on each request and redirects to the provider's signed `/iframe` destination, so every opening gets fresh authorization and a page left open never needs the reader to repair an expired link. The player supports fullscreen and never autoplays. Both routes share the backend media-access policy and return private, no-store redirects. Preserve saved attachment order, poster previews and accessible labels. Initial HTML and drafts contain Tips paths and ids only; the browser stores no playback token persistently, though the signed provider URL necessarily appears in the browser's network requests. Do not add a custom player page or an overlay gallery.

Opening a tip from filtered discovery initially shows reviews across all setups. Do not preselect review model/environment filters from the discovery page. Review filters are independent controls; explicit tip-page URL filters and browser Back restoration retain their own state.

The tip's own Prompt, Result and attachments are visible. Inside a tip's review list, each review shows its full firsthand account, setup, author, dates and actions; its optional Prompt, Result text and attachments sit together in one native `<details>` disclosure with a descriptive summary such as "Prompt and result · 2 images." Reviews default closed; a review opened through its single-review URL defaults open. Toggling is browser-local and a vote or count patch never collapses a section the reader opened. Never truncate text behind "Read more," never fetch on expand, and never nest disclosures. Preserve Markdown in the account and verbatim whitespace in prompt/result text. Attachment previews follow the saved order. The main feed remains text-only.

Use the data model's text-rendering rules for Markdown, plain text, and verbatim prompt/output blocks. Prompt and result text soft-wrap without changing copied bytes; layout-dependent code overflows within its own region. Defer text previews: no Write / Preview tabs or live Markdown preview in the MVP. Authors see rendered Markdown after publishing or saving an edit. Keep existing image/GIF previews and authorized video previews; these are attachment feedback, not text preview. The same document defines deleted and hidden content presentation, image delivery, and list behavior.

## Interaction and recovery

Back navigation and reconnect render the page named by the current URL: browse, search, profile and inbox pages, and a tip's review page and sort. Individual-review links use the single-review view below. Editor draft recovery follows its separate contract.

The notification bell opens the dedicated inbox page on both mobile and desktop. Use the existing inbox read-state behavior; do not add a notification-preview dropdown or a second preview read-state lifecycle.

Disconnected inbox mount is read-only. Once per connected visit, capture the current page and all unread `(id, count)` pairs in the backend snapshot and perform the count-matched mark-all-read operation. Page changes within the same visit do not mark again; a genuine remount is a new visit. Notifications arriving or folding after the snapshot stay unread; the existing policy still marks captured rows on later pages read. Describe the inbox as recent activity and say that opening it clears the badge; rows in the marking visit render unread from the snapshot, later pages render their actual state, and no "seen" claim is made.

The inbox shows notifications newest first, twenty per page with Previous and Next. Vote notifications read "Your tip got new helpful votes" or "Your review got new helpful votes" with the activity time; they show no numeric event total. Do not load automatically on scroll.

A signed-out vote click starts sign-in and returns to the same tip or review. Show the current vote state after authentication and let the reader click again; the earlier click does not cast a vote automatically.

On the tip page, display separate "Helpful N" and "Not helpful N" counts for the tip and each review. Update counts and the selected button from the confirmed backend response, refreshing only that row's assigns. Compact browse, filtered-feed and search summaries retain net score alongside the same Helpful / Not helpful actions. These vote controls use the same signed-out return flow and uncertain-response recovery as the tip page, and confirmed updates do not reorder the current list. Counts describe helpfulness, not successes or failures.

Helpful / Not helpful voting is available to eligible signed-in readers, without requiring firsthand use. Keep the firsthand requirement on tip and review forms. Describe scores as helpfulness, not success rates. A reader may find a review helpful even when it reports that the technique failed. Vote buttons submit the desired resulting state; show pending feedback and reconcile uncertain saves according to the [backend vote contract](backend-design.md#voting).

The tip page has one contribution control near the tip header, so it is reachable before a long body. Its state follows the viewer, resolving an existing own review first: a viewer with a review sees "Your review", linking to that review's single-review view where Edit and Delete are available when permitted, even when the parent is hidden or deleted; an eligible viewer without one sees "Tried this? Write a review"; a signed-out viewer of a live tip sees "Sign in to review"; a hidden or deleted parent with no own review shows a disabled control explaining that the tip is not accepting reviews, for signed-in and signed-out viewers alike, with no sign-in redirect to a dead end; a fully banned viewer without an own review sees no contribution control. Ownership takes precedence: a banned author still sees Your review and its permitted Delete action, including for a hidden review. The header state comes from a lightweight own-review lookup returning identity and current capability, not a rendered review. Wherever the viewer's full own review renders, in the ranked list or selected view, reuse the same action group and show Edit and Delete according to current capabilities. A live own review otherwise appears in the ranked list at its normal rank with a "Your review" badge; a hidden own review is reachable through the header link and the authorized profile/single-review path. Mask hidden/deleted parent content without removing the review’s permitted deletion path.

The MVP has no clarification-question form, general comment composer, or reply threads. Label the review action and helper text around firsthand experience; do not present it as a general discussion box. Readers can browse, vote, and publish a review after trying the technique.

An author-deleted tip's original URL shows "Deleted tip" and its existing visible reviews. Hide the deleted tip's title, content, author attribution, and attachments, including in metadata and linked labels. Block new reviews; retain the existing reviews' independent permissions.

A hidden tip's public page shows a removed-tip placeholder and its existing visible reviews, including review attachments. Do not render the hidden tip's text or attachments for ordinary readers. Disable new-review entry while hidden; if publication is rejected after an editor was opened, preserve the draft and explain that the tip is unavailable for new reviews. Existing reviews retain their own visibility and permissions.

For an author's deliberately moderator-hidden tip or review, show a generic "Removed by moderation" notice alongside the content they are still permitted to inspect. Do not display a removal reason or report details. Keep Edit available for eligible authors, and explain that saving changes does not restore visibility. This adds no notification or appeals interface; follow the [moderation contract](backend-design.md#reports-and-moderation).

A fully banned account sees one page-level explanation that it cannot contribute and can still read and delete its own tips, reviews or account; hidden controls do not each repeat it, and a refused save in an already-open editor preserves the text with the same explanation.

The review composer has three main content sections: **Review** (required textbox, displayed as Markdown), **Prompt** (optional textbox), and **Result** (optional text, uploaded media, or both). Keep the written experience distinct from the supporting prompt and result. Result uses a combined composer without a format selector, as agreed in the interview. Model and environment remain optional setup selections. See the [backend review-content contract](backend-design.md#review-content-and-evidence).

Reuse the optional Prompt and Result controls in the tip form, including the same media limits, upload states, and draft recovery. The tip form retains its title, required technique description, required tag, and existing setup fields. Share the Result component between both forms; writing a tip and reviewing an experience remain distinct actions.

Connected search changes and explicit Retry use the single async helper above: cancel superseded local work, show current loading/error state and ignore stale completions. Follow the [backend search contract](backend-design.md#task-first-discovery).

Authentication forms wait for direct Swoosh provider acceptance with a timeout and allow retry on failure. Acceptance is not proof of inbox delivery; a timeout leaves delivery uncertain: say that a link may have been sent and offer to request another. On an invalid, used or expired link say that it no longer works and offer another; promise nothing about other messages. Follow the [email delivery contract](backend-design.md#authentication-email-delivery).

Explain during an email change that successful confirmation signs out other sessions. Start a fresh session family for the confirming browser after the change commits; other browsers require sign-in with the new address. Retain the existing recent-authentication and new-address verification requirements. Failed confirmation does not sign out existing sessions.

Authentication request rate limits apply before token/mail work, including LiveView events; show the backend’s retry feedback without pretending a link was sent. Same-browser logout revokes the whole renewed session family; another browser may remain signed in. These backend guarantees do not depend on delivery of a disconnect broadcast.

### Result composer

Each image/GIF has an optional "Image description" field, stored as `media.description` (nullable plain text), with brief help drawn from the W3C image decision tree; it is not required to publish or save. Description edits travel with the content's edit version and the attachment's draft slot identity, through the same whole-content edit transaction as text and order. A supplied description becomes the image's `alt`. A missing description renders a truthful generic fallback such as "Image description not provided" with the full-size action named separately; never use a filename as alt and never treat omitted input as a decorative-image declaration. Descriptions save with the attachment, autosave in its draft descriptor, move with the item on reorder and survive restore and edits. This is an acknowledged accessibility limitation, not an equivalent alternative; record it in the launch checklist and audit real rendered pages before any conformance statement.

Authors reorder attachments by dragging previews, implemented with a maintained drag helper, and by Move earlier / Move later buttons that give keyboard and single-tap users the same operation. Use a touch hold delay so dragging does not capture scrolling; keep attachment identity, descriptions and draft order with the moved item; disable the unavailable direction at the ends; preserve focus on the moved attachment and announce its new position. Neither a drag-only tray nor four always-visible buttons per item is acceptable. Verify long-distance and middle moves with a full ten-item tray. Reordering changes form state, is autosaved, and persists only with Publish or Save; it does not re-upload assets.

Represent intended order as `media:<id>` for retained/staged records and `upload:<ref>` for pending LiveView entries. During video preflight, replace that video's provisional token in place with its durable media id, preserving its position and visual identity; do this before transfer completes. Keep transient entry references for transfer UI only. Render account/form identity, order and recoverable media references as hidden inputs for autosave/reconnect. Content validates every token's ownership, target, uniqueness and combined limit; never submit arbitrary R2 keys.

Use LiveView's external-upload API for videos: a `:videos` configuration with `auto_upload: true`, the 1 GB limit and a preflight callback to `Content.begin_video_upload`. The callback performs fresh admission and target checks, then returns the server-issued endpoint and media id. A small JavaScript uploader adapter runs tus-js-client for every video, including small files, and reports progress/errors through LiveView's entry callbacks. Resumability shields users on unreliable mobile connections. Browser progress never grants readiness or publication.

Images/GIFs use a separate upload-on-submission configuration. Per-configuration `max_entries` cannot enforce the shared ten-item limit including retained attachments; check the combined selection in the page and backend. A thin browser adapter may route mixed paste/drop selections to the appropriate configuration. Reuse LiveView's entry handling rather than building a parallel selection/progress subsystem.

Persist the video media id and position in the form and account-scoped local draft as soon as preflight returns. At submit, external-entry consumption yields metadata only; publication still validates the durable row through Content. Keep the durable reference after a failed submission even if the transient entry has been consumed. Recovered completed videos need no live upload entry.

Wire view errors and cancellation explicitly in the tus adapter. Pause/resume an interrupted transfer against the same asset and still-valid endpoint; reselecting the source file must not silently create a second asset or extend authorization. Closing the browser may require reselection and does not promise continued transfer. Explicit removal invokes guarded discard/cleanup; a view error alone does not delete a possibly completed asset. Verify the real uploader in a browser: LiveView's simulated external-upload tests do not execute tus or provider requests.

Show that unfinished video transfers must complete within one hour of authorization. Resuming does not extend the deadline. When it expires, preserve the text and attachment position and offer a fresh upload or removal. Completed uploads instead follow the separate 48-hour draft-video recovery period, including while processing.

Show image/GIF limits of 10 MB per file and 50 MB total for newly selected images/GIFs per submission, using decimal MB. Count only new files toward that byte total when editing; retained attachments still count toward the shared ten-attachment allowance. Reject oversized selections with file-specific or aggregate feedback while preserving text and other valid selections. Videos retain their separate 1 GB per-file limit.

The page LiveView owns form state and events, including validation, recovery, attachment selection/status and submission. Share Prompt/Result rendering through function components and reusable behavior through ordinary functions; no second form state lives in a Result LiveComponent. Backend contexts own durable state and permissions; hooks handle browser-only capabilities.

Maintain one page-owned bounded async status cycle for pending videos. Start or restart it whenever the pending set changes, including preflight, draft restore and an action patch; cancel the prior chain and avoid overlapping cycles/timers. Call `Content.get_video_uploads(scope, ids)` only for selected owned pending ids. It refreshes pending state through bounded provider reads, applies guarded writes, and returns committed state; ready rows need no read. ### Saving and recovery

The form/hook identity includes the current account and intended form. Restore from IndexedDB only on fresh hook `mounted()`, never from `reconnected()`; inspect the current DOM against the initially rendered form baseline before reading that account/form's IndexedDB record; the author may have typed before the hook started. Then use the autosave `input` listener to track typing during the asynchronous read. Absence of a server `phx-change` is not proof of a pristine form. Apply a saved draft only while pristine. If typing has occurred, preserve it, pause conflicting autosave and offer explicit reload. Do not disable the editor for the entire storage read: storage delays are not bounded.

When applying a restore, briefly disable the fieldset until the restore reply so typing cannot race application. Reconcile a pending publication key first, then validate original versions and authorized media references. Enable autosave after recovery settles, not merely when the push is sent. No-record and storage-error branches allow composing without a restore reply; storage failure never blocks publication. Ignore late results after hook replacement/destruction or after falling back to composing without restoration. Do not introduce a general recovery-generation framework.

For a same-page reconnect, use LiveView form recovery of current DOM values, without another IndexedDB restore. A remount may be a new server process, so stable IDs do not remove the pristine-DOM, typing and stale-callback guards. Use one explicit `phx-auto-recover` handler when ordinary validation cannot also express pending-publication reconciliation, identity checks and quiet error presentation. Check the recovered account/form identity against the fresh mounted identity before accepting values; a hidden owner id is a recovery guard, never authorization. Preserve the original edit version and complete base, submission key, active draft identity, handoff mode/target, blanks and intended attachment order. Review setup defaults initialize only once for a fresh form. Recovery must not trigger publication or new validation errors on focused/untouched fields. Keep an unresolved submission's values fixed until its outcome is reconciled.

Use IndexedDB for browser drafts. Each record has a `draft_id`: the submission key for a new tip/review, or a local UUID for an edit draft. In one read/write transaction, compare `(draft_id, revision)` with the editor's expected pair, then save and increment the revision only on a match. Apply the same guard to discard and post-save clearing. A missing or replaced record is a conflict for a stale editor, even if a new draft reused the same numeric revision. Only explicit creation of a new draft may insert a missing record; concurrent first creation must detect an occupied account/form key. On conflict, preserve on-screen input, pause autosave, and offer explicit reload of the saved draft. Keep the existing account/form scoping and distinguish this browser revision from the server's content edit version.

This uses [IndexedDB's transactional storage](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API) to implement the agreed cross-tab behavior. Store text, selections, submission keys, recoverable attachment references and image descriptors (filename, type, size, order, description; never bytes); image/GIF files still require reselection after reopening. If storage is unavailable or a transaction fails, follow the existing compose/publish-without-autosave behavior. Do not add a second browser storage mechanism or server draft fallback; server-side drafts are deferred because network-dependent persistence weakens interruption recovery.

Autosave unfinished edits in the same browser, scoped to account and content id. At initial `get_edit_form`, store the original `edit_version` and a complete immutable base of normalized author-editable fields: text, tag/setup including explicit blanks, and ordered media ids/descriptions. Use Content’s canonical normalization/comparator, not a second browser ruleset. Exclude counters, timestamps and moderation state. Autosave, restore and failed saves never change the base; replace it only when the author explicitly loads the latest version. Missing/incomplete base disables the safe-conflict shortcut. Restore input and authorized attachment references, then recheck current state before saving. Preserve text on conflicts or lost eligibility. Existing attachments need no reselection, new images do, and staged videos recover only until expiry. Discard never deletes published attachments.

Validate tip and review text on submission, not on blur. Before the first submission, untouched fields never show errors and typing is never interrupted. State limits up front as helper text; never set `maxlength` on any field, because it silently truncates pasted text, and return the server's length error with the input preserved instead. Publish and Save validate the entire form, including required fields the author never touched, preserve all input on failure, and show field errors with a focusable summary linking to affected fields; focus moves to the summary. After the first failed submission, revalidate corrected fields on change so stale errors clear; errors otherwise describe the last attempted submit. Use one validation presentation, not native bubbles competing with the summary. Keep attachment format and size validation immediate. Autosaving a draft and reconnect recovery do not trigger publication validation. Validate text before consuming images so a missing body does not start an R2 attempt. The draft hook reads current form values on browser `input` events with its own debounce. No second validation ruleset or server autosave event is needed. Flush pending local writes where possible before navigation, without promising unload durability.

If browser autosave fails or storage is unavailable, let the author continue composing and publishing without a saved draft. Keep input on screen; do not block the editor or claim that the draft was saved. The leave-confirmation rule still applies to work that would be lost. No server-side draft fallback is added.

Ask for confirmation before leaving an editor only when recoverable work is at risk: current text or selections have not autosaved successfully (including a draft conflict), newly selected images/GIFs need reselection, or a video transfer is unfinished. A safely saved draft with recoverable uploaded videos needs no confirmation, even while those videos are processing. Derive the risk from the saved, dirty, conflict and file state the editor already holds. Apply this to in-app navigation and use the browser's native leave warning where supported for reload or close. Warnings are best-effort, especially on mobile; continue autosaving independently. Leaving is not discarding, publishing, or cancelling server-side video processing. Label the ordinary exit "Leave editor" or "Back to tip" with the local-draft status beside it; reserve "Discard draft" for the explicit destructive action. Confirm discard once, explaining that it removes the saved draft and its unpublished changes; cancelling keeps the draft and editor input. Successful discard does not trigger a second leave warning for the discarded work; a resumed form says it is a recovered draft with its save time. Use ordinary anchors in the editor layout for exits, including logo, Leave and account links, so a conditional native `beforeunload` handler covers full-page navigation as well as reload/close. Audit these exits for accidental live navigation. Remove the handler when risk clears; confirmed save clears risk before application navigation. This remains best-effort and does not replace autosave.

Present loading, validation errors, disconnection, and reconnection as normal interface states. Show a confirmed save only after the backend confirms the required durable write. An interrupted response may leave the outcome uncertain; reconcile with stored state before presenting a final outcome. Use one saved/recovering/published vocabulary: "Draft saved in this browser at 10:42," "Draft couldn't be saved; keep this page open," "Images need reselection," "Video uploading / processing / ready," "Checking whether your post published" as a fixed-values state, and confirmed "Published" or "Changes saved." Never expose submission keys, version numbers, worker names or provider details to authors.

Update the page after the user's actions. Automatic feed reordering and notification broadcasts are not added by choosing LiveView; follow the existing product decisions.

If another tab has changed the same stored draft, pause conflicting autosave and keep this tab's input visible. Explain the conflict and offer to reload the saved draft, clearly stating that reload replaces the current input. Do not silently overwrite either the saved draft or this tab's form, and do not attempt automatic merging. Use draft identity-and-revision checks for autosave and draft clearing.

Keep one recoverable new-tip draft slot per account in this browser. New tip resumes it; offer once-confirmed Discard before another draft. Review slots remain separate per parent, and ordinary edit slots per published item. The explicit handoff below keeps its active record in the original new-draft slot; New tip then identifies it as an unfinished proposal to edit the named item, with Continue and Discard. No draft list or third record is needed. Leaving is not discard, and discard cannot undo a publication whose confirmation was lost; reconcile uncertain operations first.

Autosave unpublished text, selections, submission keys, recoverable upload ids and image descriptors in the account/form record. Before Publish, flush the local revision CAS when storage is available. A conflict preserves input and pauses autosave; failed/unavailable storage still permits explicit publishing with at-risk feedback. The local CAS does not atomically coordinate remote publication. On reopen, use one bounded `get_publication` lookup, supplying complete intent when available, before restoring a new-publication composer. Absent permits explicit same-key Retry but does not prove an earlier request stopped; lookup failure stays unresolved with Check again or Sign in. Keep an unresolved attempt’s values fixed. Missing image slots cannot be treated as an empty media selection. If clear CAS fails, preserve newer work and do not label it published; if unsaved on-screen work remains, do not navigate it away. Follow the [backend receipt contract](backend-design.md#publishing-and-retry-contract).

Images and GIFs travel through the app on submission. Videos upload directly to Stream on selection using backend-issued URLs. The backend owns authorization, trusted readiness checks, attachment, and cleanup for both paths. Clicking Publish is required after video readiness; completion events do not publish the review. Start synchronously; page ownership of the entries is the invariant, not synchrony itself. Consume only after the submitted content is acknowledged as created/equivalent or its explicit edit is confirmed; known failures retain selections while the page lives, including a definite rate-limit rejection, which shows when to try again and needs an explicit retry with the same submission key. Disable form/attachment changes during the attempt. On unknown outcomes reconcile first; neither page termination nor discard proves rollback or authorizes deleting uncertain R2 objects. No temporary file path outlives its owning entry, and no page-held R2-key staging scheme is needed. Reopening still requires image reselection. If realistic submissions demonstrate harmful page-message blocking, use one page-owned `start_async` attempt with immutable inputs and retained paths; the page consumes entries after confirmed success. Reject overlapping attempts and attachment changes server-side, treat task termination as potentially uncertain, and test the pinned upload-file lifetime. No detached task, Oban job or second staging system is added.

An edit form retains its original expected version and complete editable base. On stale-save rejection, fetch current authorized state and compare its editable fields with that base through Content’s shared comparator. If equal, offer explicit Save at current version, retaining the proposal and using the fresh version through the normal server guard; another race may still reject it. This avoids manual retyping for a moderation-only change while preserving hide/restore version protection. Never auto-retry or advance the base/version on restore or autosave.

If editable fields changed or the base is unavailable, preserve the proposal as one labelled, selectable, read-only reference in the same revision-guarded record. Let the author explicitly load the latest content/base/version and reapply changes. Autosave resumes after that load settles; the reference stays until confirmed save or explicit dismissal. A repeat conflict pauses until the existing reference is resolved rather than replacing it. Storage failure keeps the reference on screen as at-risk work. Do not automatically merge or restore destroyed attachments. An unknown edit outcome reloads current saved state while preserving input and follows the [backend edit contract](backend-design.md#editing-and-conflicts), never blind replay with a new version.

When the linked review is unavailable, keep the tip context, show "Review deleted by author" or "Review removed by moderators" when the backend supplies that authorized state, otherwise "Review unavailable," and offer the same Show all reviews link. Do not substitute a different review.

Empty states are one line each, distinct from retrieval errors: "No tips yet" on an empty feed, "No tips match these filters" for a filtered empty result, per-filter copy on an empty profile list with the contribution link shown only when the viewer is eligible, and an inbox line covering helpful votes on tips and reviews and new reviews. No illustrations.

### Holistic consensus acceptance

- Complete early vertical slices: text publication/edit with lost confirmation, one retained image after a known rejection, one private video through its lifecycle, and another-browser magic-link return. Run pinned search integration alongside these slices.
- Race two different drafts under the same publication key, including a fixed retry and unknown image identities. Verify equivalent-only clearing and preservation after CAS/storage failure.
- Recover a divergent proposal with selected images and ready videos into Edit without reselection/re-upload. Keep an unrelated edit draft unchanged through save/discard. Exercise missing storage, lost edit response, Back, refresh and reconnect; stored edit mode must not become new publication mode.
- Restore a draft after moderator hide/restore and use the explicit unchanged-base shortcut; preserve hiding. Retag, description/media changes, incomplete base and a second race must use the correct conflict path.
- Verify a fully banned author reaches a hidden own review through Your review and deletes it, including under a hidden/deleted parent, while Edit remains unavailable.
- Rapidly change queries/pages, cancel tasks and deliver stale responses; show only current results and no cancellation error. Unchanged ordinary submit does no work; same-URL Retry starts fresh work without a history entry.
- Test hook mounts and reconnects with typing before/during storage reads, action-patch identity, ignored preview subtrees and server-rendered errors, pending-video additions/removals and delayed status results. Audit every editor exit, including logo/account links.
- Verify family logout and failed disconnect delivery stop privileged work without forced reload; reauthentication preserves account identity and the validated return destination, with no automatic vote/report/save/delete.
- Measure ten delayed attachments and thirty maximum-size full reviews for responsiveness, memory, HTML/connected-render size, focus and reading behavior. Use the existing page-owned async publish option only if measurement warrants it; do not add another upload store, client cache or truncate the agreed review content.

These are acceptance requirements, not executed browser-test results.
